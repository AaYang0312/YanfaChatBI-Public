# PostgreSQL 视图问数支持

状态：已实现，默认关闭。通过 `QUERY_OBJECTS_ENABLED=true` 开启。

## 背景

原有对象选择器只列出普通表。业务侧经常把复杂口径封装在视图中，用户希望：

- 在聊天里选择视图作为查询对象
- 只拥有视图权限、没有底表权限的账号也能问数
- 表与视图使用同一套选择、检索与生成流程

## 设计

### 1. 统一对象目录

表与视图统一表示为 `schema / name / kind`，`kind` 取 `table` 或 `view`。

- `table`：读取 `information_schema.tables`
- `view`：读取 `information_schema.views`
- 只投影当前账号可见的对象，不额外授予底表权限

### 2. 显式选择

选择状态包含：

```json
{
  "schema": "public",
  "name": "sales_daily",
  "kind": "view"
}
```

规则：

- 空选择与 `ALL` 仍只包含表，保持旧聊天行为
- 视图必须显式选择，或在 `include_kinds` 中明确包含 `view`
- 选择使用 `selection_revision` 做乐观并发控制，旧客户端不能覆盖新选择
- 旧聊天没有 v2 选择时继续走原有表路径

### 3. 权限边界

- 视图按自身权限执行（`security_invoker` / owner 视图行为由数据库决定）
- 不因查询视图而授予底表 `SELECT`
- 目录读取失败、定义不可见、列权限不足时返回明确原因，不猜测结构

### 4. 生成与执行

- 提示词同时支持表和视图，明确当前对象类型
- 生成前只读取已选对象的结构，不扩大到同 schema 其他对象
- 执行前做只读判定：`SELECT` / `SHOW` / `EXPLAIN` / `VALUES` / `TABLE` 及只读 CTE 走查询路径
- 视图查询与表查询共享分页、超时、取消和结果摘要逻辑

### 5. 检索

视图对象写入独立集合（默认 `<schema>_objects_v2`），不覆盖旧的表结构集合：

- 过滤条件包含连接、schema、`kind`
- 视图名称、注释与列信息参与向量化
- 关闭开关时不写入、不检索视图对象

## 兼容性

| 场景 | 行为 |
| --- | --- |
| 旧聊天（无 v2 选择） | 继续使用原有表选择 |
| 新聊天只选表 | 与旧行为一致 |
| 新聊天只选视图 | 只查询视图，不读取底表结构 |
| 关闭 `QUERY_OBJECTS_ENABLED` | 选择器不展示视图，已有视图选择保持停用 |

## 验收要点

- 只读账号在仅有视图权限时可以完成问数与可视化
- 撤权后下一次查询返回明确错误，不缓存旧结构继续生成
- 视图与表混合选择时，生成只使用已选对象
- 旧客户端不能通过覆盖选择把视图聊天改回 `ALL`
